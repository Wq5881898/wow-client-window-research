# 13. 输入注入风险说明（SendInput / 驱动 / 硬件）

> 2026-11-05证据更正：本文为旧风险登记，未记录对应的设备名、驱动标志或硬件检测实测；撤回“软件层零痕迹/无法区分”的绝对表述。SendInput的低级钩子注入标志与Raw Input设备枚举是不同机制，不能把“事件必带虚拟设备名”当已验证事实。驱动许可证、反宏冷却触发机理及正式客户端表现尚未重新核实，旧表不作为升级驱动/硬件通道的执行建议；当前范围仍为本地客户端输入验证。

更新：2026-10-19
性质：技术风险登记。不是法律意见，不证明任何方法已获授权或不可检测。
适用边界：本文区分 **本地 AzerothCore 私服实验**（当前阶段）与 **官方客户端（正式服 / WoW Forever）** 两个场景。私服无风险 **不等于** 官方场景无风险。

## 一、背景

当前主路径的执行段是进程外标准输入（docs/10、docs/11 已定）。本地实验中遇到的实际问题：3.3.5 客户端使用 Raw Input，`PostMessage` 注入的窗口消息不被接收，因此实验通道转向 `SendInput`。

由此引出两个独立的官方场景风险问题：

1. **可检测性**：官方客户端能否在技术上区分注入输入与真实键鼠？
2. **合同性**：即使不可检测，注入输入是否落入 EULA 对 bot / 自动控制的禁止范围？

两者相互独立：不可检测不等于获授权；当前未处罚不等于条款允许。

## 二、输入注入技术分级

| 层级 | 方法 | 游戏是否接受 | 注入痕迹 | 部署代价 |
|---|---|---|---|---|
| L1 窗口消息 | PostMessage / SendMessage | 否（Raw Input 客户端不接受） | 消息队列来源可查 | 最低 |
| L2 会话注入 | **SendInput**（当前实验通道） | 本地3.3.5a已验证 | Windows低级钩子有注入标志语义；本项目未测设备身份或当前客户端检测实现，不推断必有虚拟Raw Input设备名 | 低，纯用户态 |
| L3 驱动注入 | Interception等驱动 | 本项目未实测 | 输入来源标志、设备路径和驱动检测差异须按实现核验，不承诺无痕 | 需安装/签名；许可证与商业授权须按具体版本原文核对 |
| L4 硬件盒子 | USB HID模拟设备 | 本项目未实测 | 设备描述符、输入行为及其他检测面仍存在，不能声称软件层零痕迹或无法区分 | 需额外硬件；本项目未部署 |

补充事实：

- 项目既有纪律（docs/10）：进程内存、注入 DLL、封包注入属高风险对照层，不在落地路径。L3/L4 是“输入通道升级”，不是内存/封包路线，但仍各自引入新的检测面（驱动枚举、USB 设备枚举）。
- 公开可查的 2016 Anti-Cheating Agreement 观察面为 RAM、游戏进程及附加代码、进程列表、句柄列表（docs 附录B）。该枚举是历史事实：未提及输入注入，但**不能据此推出输入注入不可检测**。Forever 当前实现未知。

## 三、官方场景风险清单

### 3.1 客户端反宏机制（行为层，换通道无效）

- 正式服与 Forever 的“机器人冷却”（15 秒施法延迟）机制公开描述为：当某按键在**没有可观察的真实输入活动**的情况下被连续按下时触发。
- 该机制检查的是“真实输入活动是否存在”，不是“本条输入是否带 injected 标志”。**SendInput、驱动注入同样可能触发**；L4 若盒子与人工输入共享同一 HID 设备路径则同样受此逻辑约束。
- 对预研的意义：反宏冷却是否触发、以何种条件触发，本身应作为 T2 输入实验的**观测项**记录，而不是规避目标。

### 3.2 检测面（技术层）

| 风险点 | 说明 | 影响层级 |
|---|---|---|
| Raw Input设备身份 | 本项目未测SendInput与Raw Input设备的对应关系，不能断言事件必携带虚拟设备名 | 待核 |
| 注入标志 | 若客户端装低级键盘/鼠标钩子，可见 `LLMHF_INJECTED` / `LLKHF_INJECTED` | L2 |
| 驱动枚举 | 机器上存在 interception 等输入驱动，可被句柄/驱动列表观察 | L3 |
| USB 枚举异常 | 硬件盒子的 VID/PID、设备描述符可能与任何真实外设不匹配 | L4 |
| 行为特征 | 间隔方差过小、无微动、无闲置、反应时间过分布——与注入层级无关，任何自动化都暴露 | 全部 |
| 进程/句柄关联 | 控制台/注入器进程与游戏同时存在（L2/L3 在目标机上有进程；L4 控制端可外置） | L1–L3 |

### 3.3 合同层（与检测无关）

- EULA 禁止 “not expressly authorized” 的自动化控制（bot 定义）。**用哪条输入通道不改变“谁在做决策”**：若决策来自外部程序，L4 与 L1 在合同事实上同类。
- Beta / Forever 环境的 `Consent to Monitor` 类条款扩大监控授权面；Forever 专项条款尚未检索到（docs 附录B 负面检索）。
- 历史先验：MDY 案涉及商业销售与检测规避，不决定个人测试场景，但表明“技术上不可见”从未是合同抗辩。

### 3.4 处罚不确定性

- 官方处罚（警告、冻结、封禁）的触发条件、证据标准与申诉结果均无公开逐项承诺。
- 本项目的立场：承担个人账号测试风险是**用户已确认的决策**（docs/08），该决策针对的是“做真机观察”，不应被扩大解释为“接受任何注入方式在正式服长期运行”。

## 四、场景结论

| 场景 | 结论 |
|---|---|
| 本地 AzerothCore 私服 | **无账号处罚风险**（无 Warden、无官方账号）。SendInput 可直接使用，目标是打通闭环与采集探针数据。 |
| Forever 正式测试 | SendInput 起步（与主路径一致）；反宏冷却触发情况作为观测项；账号风险自担，建议一次性、短时、低量实验。 |
| 输入通道对照 | L3/L4的兼容性、许可和检测差异未实测；本文不据此安排升级。当前继续验证已选SendInput链路。 |
| 商业化 / 多人服务 | 合同问题优先于技术问题：未取得 `expressly authorized` 状态前，任何层级都不构成安全区。 |

## 五、观测项（供 T2 实验记录）

1. SendInput 后客户端是否出现 15 秒反宏冷却；触发前的按键次数/频率。
2. 注入输入的间隔、持续时间与人工输入的分布差异。
3. 客户端进程中是否可观察到新增钩子、驱动句柄或设备枚举变化（只读观察，不修改）。
4. 每次实验的 build、会话、时长、账号类型，全部记入结果契约，与私服记录分列。
