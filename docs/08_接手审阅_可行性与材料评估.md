## 1. 可行性判断

当前只能给出分层判断，不能给出“自动化已可行”或“自动化已否证”。

### 1.1 作为预研项目：可以继续

仓库已经具备继续研究所需的最低结构：来源归档、静态 API 对账、条款取证、合成模型、输入仪器 dry-run、证据类型纪律，以及用户决定记录。在这个意义上，项目不是空转文档，而是一个尚未进入目标客户端的测量准备态。

### 1.2 作为 Forever 个人账号自动化技术结论：尚未成立

用户目标是评估个人账号自动化的技术可行性。最小讨论场景是固定区域、固定目标、全程旁观，但不代表最终产品范围。

现有材料能够支持的，只是若干可证伪工作假设：

- 归档文档列出了位置、Unit、Assisted Combat、限制状态、拾取/容器等接口表面。
- 固定目标和固定区域可能减少敌人集合与导航感知，但不能从静态资料确定剩余视觉或状态工作量。
- Assisted Combat 可能减少职业循环维护，但不提供目标发现、移动、输入执行或完整战斗安全信息。
- G6 旧枚举假设已被静态反证；这只否定该枚举方案，不否定采集观察本身。采集也不属于当前讨论的固定目标场景。

现有材料明确不能支持的：

- 目标 build 与归档镜像一致。
- 任何 API 在目标客户端可调用、返回可读、跨场景稳定。
- 外部输入被游戏接受并产生预期效果。
- 观察与输入能够组成个人账号自动化闭环。
- 当前反作弊实现、处罚概率、检测面。
- Forever/Beta 客户端附加条款的具体内容。

没有目标客户端，技术可行性仍是开放问题。API 名称存在、仿真击杀数、历史 bot 市场，都不能代替真机证明。

### 1.3 合同与发布边界：技术实验不等于获准

2026-09-22 归档的现行公开 EULA 文字直接覆盖未获明确授权的 bot / 角色自动控制、data mining、unauthorized connections，以及 Beta 与监控相关条款。2009 来源的 UI Add-On Policy 仍公开，但不能单独回答 2026 Forever 的付费内容、外部数据路径或自动控制。

这些是合同文字和历史先验，不是个案授权结论，也不是目标法域法律意见。它们足以否定“只要不读内存、没有拦截事件就等于允许”。它们不能逐项裁定诊断 addon、SavedVariables、屏显、截图或单次外部按键的适用范围。

用户决定是：个人账号技术实验不等待 15C，并自行承担账号处罚风险。该决定是风险承担，不是 Blizzard 授权、低风险证明或发布许可。发布、分发、招募他人测试和商业化尚未由用户决定；历史 MDY 材料只说明特定商业规避事实下的高风险先验，不能外推到本项目未发生的发布行为。

### 1.4 最小场景的条件可行性

若把问题收窄到“固定区域、固定目标、全程旁观的个人实验”，静态资料给出的是一条比任意开放世界更短的未知项清单，而不是一条已验证路径。该场景仍然依赖尚未观察的能力：

- 玩家位置是否以可用形式到达外部程序。
- 玩家已选手动目标后，哪些 Unit 状态可读，哪些是 NIL / SECRET / ERROR / FORBIDDEN。
- 目标失效、额外敌人、死亡和恢复如何被发现。
- 外部输入是否产生游戏内动作。
- 这些观察能否在具体 build 和具体场景中维持足够稳定，以组成闭环。

在线端点的少量历史样本处于秒到数十秒量级，并出现空响应和 429。这只支持“所测端点不适合低延迟热循环”，不支持“所有在线模型无价值”。合成仿真 v4 可以比较模型内策略和发现代码回归，其击杀、死亡、卡住和配额数字不是 Forever 指标。

### 1.5 总评

| 问题 | 当前判断 | 证据类型 |
|---|---|---|
| 预研能否继续 | 可以；材料与方法已足够支撑下一轮观察 | 文档与仓库状态 |
| 个人自动化技术是否可行 | 未知；静态表面足够提出假设，真机空缺 | 工作假设，无运行时观察 |
| 固定目标是否降低感知复杂度 | 合理假设，未证实剩余工作量 | 工作假设 |
| 输入能否驱动游戏 | 仪器存在；未发送真实输入 | 工具 dry-run |
| 个人实验是否获 Blizzard 授权 | 无；用户只决定自行承担处罚风险 | 用户决定 + 合同文字 |
| 发布或商业化是否可行 | 未开放；无授权依据 | 未决事项 |

可行性的主要阻塞不是文档不足，而是没有目标客户端上的观察。在取得 build、调用、值状态、输入效果和条款缺口记录之前，不应把项目写成产品验证或能力证明。

## 2. 文档与仓库质量

校准后的材料质量高于普通预研笔记。优点集中在证据纪律；不足集中在仪器未完成、一次性脚本和少量内部不一致。

### 2.1 优点

1. **证据类型被显式分开。** 索引第 4 节和主报告证据账本把文档化表面、工作假设、运行时观察、合成结果、用户决定拆开，并反复声明它们互不替代。这是本仓库最有价值的资产。
2. **用户决定与助手提案已分离。** `docs/03` 记录了原始回复、助手展开标签、当前决定和已撤销规则。`1C/5B/11A/14D` 不再被写成现行路线。这对后续接手非常关键。
3. **静态反证被保留而不是被抹掉。** G6 四枚举成员失败、lint 退出码 1、采集不等于当前固定目标场景，都写进了结果和附录。项目愿意留下负面发现。
4. **来源可追溯。** 条款取证记录带 URL、抓取日期、字节数、SHA-256 和提取脚本；损坏响被标记为不可引用。API 转储来源被标明为第三方 GitHub 镜像，不是本机客户端提取。
5. **仪器有防误触发设计。** T2 默认 dry-run、live 需精确短语、前台标题复核、不保存窗口标题和身份信息。探针数据模型把 call / value / event / effect 分列。这些是测量完整性，不是路线 gate。
6. **Git 基线可用。** 独立仓库、本地身份、`sources/**` 保留原始字节、忽略缓存与 `.env`。当前没有 remote，因此它是历史与回退工具，不是异机备份。

### 2.2 不足

1. **真机仪器仍停在设计层。** `docs/wow自动化-探针设计-00.md` 和 T1 清单定义了 Lua 记录契约与候选组，但仓库中没有可在客户端加载的探针 addon，也没有 SavedVariables / 屏显 / 聊天出口的实现。下一轮若进入真机，缺的不是更多综述，而是可运行的只读探针。
2. **命名债务仍在。** T1、T2、G1–G10、15C 仍出现在文件名和正文中。当前文本大多声明“名称不是 gate”，但新读者仍可能把它们读回阶段链。这是可读性问题，不是现行规则复辟。
3. **附录日期不完全统一。** 附录 C–F 仍标“2026-09-22 校准版”，主报告和交接文件为 2026-09-23。内容经抽查与现行纪律一致，但版本戳会让人怀疑是否全部经过同一轮校准。
4. **T2 dry-run 记录与文档略不一致。** `results/t2_input_probe_dry_run.json` 中 `records` 为空数组，`summary.not_sent` 为 3。`docs/07` 写成“3 条记录均为 `not_sent`”。代码在 dry-run 路径不生成逐次记录，只把 `args.trials` 写入摘要。该差异不影响“未发送真实输入”的事实，但属于结果契约不完整。
5. **研究脚本质量分层明显。** `api_lint.py`、`t2_input_probe.py`、`lat4.py`、法律提取脚本较完整；`audit.py`、`audit2.py`、`w3.py`、`w4.py`、`lat.py`/`lat2.py`/`lat3.py` 是一次性探索代码。后一组存在网络回写 dumps、控制台编码损坏、以及历史端点/环境变量名硬编码。附录 G 已说明它们是历史仪器，但仍可能被误当成当前运行配置。
6. **合成模型外部效度未建立。** v4 修正了隐藏世界读取和校验路径，这是有效的代码事实。模型动作集、伤害、卡住和云故障都是合成参数。文档对此有正确边界，但附录 H 的 18 行表仍容易被后续读者当成性能证据。
7. **来源有重复和未钉死风险。** `sources/forever_dumps/` 与 `sources/参考原始资料/` 中存在同名或相近 dump。`api_lint.py` 含上游 raw URL；若未冻结地重新下载，静态证据可能漂移。
8. **无远程备份。** 交接索引已写明。审查前 ZIP 与会话审计在仓库外。本地 Git 不能替代异机副本。
9. **市场材料几乎没有信息量。** I01 是真实但未完成的访谈；受访者给出广泛自动化诉求后终止。现有文档已正确限制其证明力。它不能支持需求、定价或产品形态判断。

### 2.3 文档质量总评

就“防止把自己的推测写成项目事实”而言，当前文档质量高。就“下一步能直接在目标客户端上跑”而言，文档超前于可执行仪器。主报告、交接索引和三条校准文件已经足够作为唯一入口；其余文件是附录和历史方案改写，不应再平行生长第二套路线。

## 3. 后续工作

下列内容是评估建议，不恢复 T0–T3/D1、不设 `99%` / `500 ms` / `30/30`、不把 W1 或产品 B 拉回技术主线、不把 15C 设为个人实验阻塞。具体做哪一项，仍取决于用户尚未决定的测试机、build、第一项观察范围，以及是否研究更高风险操作实现。

### 3.1 不要做的

- 不要在没有目标客户端的情况下继续扩写可行性综述。
- 不要把仿真表、API lint 绿色计数或历史竞品写成真机证明。
- 不要实现或启用向游戏窗口发送输入，除非用户明确指定测试机、窗口范围和单次实验边界。
- 不要把高风险技术从“非操作性预研”推进到操作实现，除非用户另行决定。
- 不要恢复市场访谈或产品 B 主线，除非用户决定恢复。
- 不要把发布、分发、多人测试或商业化当作下一步默认动作。

### 3.2 高信息量的下一层工作

在用户指定测试机和客户端 build 之后，信息量最高的是互不绑定的只读观察，而不是闭环 bot：

1. **记录目标 build 与限制状态。** 对照归档镜像，记下 `GetBuildInfo`、addon security、限制事件是否出现。没有这一项，其余 API 结论都可能绑错版本。
2. **实现并加载只读探针 addon。** 按现有四维记录模型写最小探针，持久化到非身份字段。先测调用是否返回，再测值是否可读。
3. **独立取样玩家位置。** 静止和玩家手工移动下记录 map ID、返回、NIL/SECRET/ERROR、间隔和抖动。这是固定区域场景的第一关键未知项。
4. **独立取样已选目标后的 Unit 状态。** 用玩家手工选择目标，按 API 分列 call/value/event，不要把 Unit 整体判可用或不可用。
5. **独立取样 Assisted Combat。** 无目标、选中目标、手工战斗、换目标。只记录返回形态，不把它解释成完整循环或授权。
6. **如需数据出口，分开测 SavedVariables / 聊天 / 屏显。** 三者机制不同，不能用一个“数据路径可用”结论覆盖。

这些观察可以单独开始或单独停止。任何一项的失败只否定该项假设，不自动否定其他项，也不自动要求转向视觉或其他架构。

### 3.3 输入与闭环

T2 仪器已经具备 dry-run 和 ABI 检查。在只读观察给出“哪些状态能被看到”之前，真实输入不是最高信息量步骤。若用户之后决定做单动作实验，仍应保持：默认不发送、逐次确认、前台复核、人工 effect 标签、不保存识别性窗口标题。`SendInput` 成功、游戏有无效果、有无限制事件、是否获授权，继续分列。

固定目标闭环只有在观察集合和输入效果都有记录后，才值得作为合成问题提出。在此之前编写战斗状态机，只会把仿真假设写得更长。

### 3.4 条款与备份

个人实验不等待 15C，但仍有低成本、非阻塞的证据工作：

- 若安装客户端，记录安装/首次启动/登录是否出现附加条款。这是当前公开检索的缺口，不是询问 Blizzard 的 gate。
- 为仓库建立异机或远程备份。当前 Git 只有本地历史。

专业审查和官方询问仍是未决事项，不是本轮技术观察的前置条件。

### 3.5 仓库内可择机清理，但不是主线

若用户同意改仓库而不改研究结论，可择机处理：统一附录日期戳、修正 T2 dry-run 的 records/summary 契约、给一次性脚本加“历史仪器、勿当作当前环境”的文件头、钉死 dump 来源、避免 `audit*.py` 覆盖归档。这些清理提高可维护性，不增加技术可行性证据。

## 4. 审阅结论

项目已经完成一次有效的自我校正：把助手设定的阶段、阈值和产品转向从规则降为历史，把 API、仿真、条款和用户决定分开。作为 Forever 个人自动化预研，它现在处于“静态假设已形成、真机证据为零”的状态。

可行性未知，不是可行性为负。未知项要靠目标客户端上的分列观察来收缩，不能靠继续润色报告来收缩。用户已选择直接技术验证并承担个人账号处罚风险；在该前提下，下一步若发生，应优先记录 build、位置、已选目标状态和 Assisted Combat 的只读结果，并把输入、闭环、高风险方法和发布问题留到用户明确决定之后。
