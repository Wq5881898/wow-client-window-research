# 客户端朝向闭环实机验收

## 结论

朝向闭环在真实客户端上验证通过。

`results/client_facing_loop_1793539713526455500.json`：`FACING_LOOP_PASSED`。

| 项目 | 值 |
| --- | --- |
| 目标 | GUID `0xF130000071000D70`，120 血，射程内（`spell_range=1`） |
| 转向后首次施法 | 失败，`last_error_reason = 5` |
| 转向闭环步数 | 6 步（每步约 10°） |
| 闭环后施法 | 成功，`cast_succeeded` 1 → 2 |
| 目标血量 | 120 → 99（实打掉 21 点） |

证据截图 `.cache/desktop-check/client_facing_loop_1793539713526455500_02-behind-cast.png`
上客户端自己的红字是：

> Target needs to be in front of you.

与探针报告的原因码 5 完全对应。

## 为什么需要协议 v5

2026-10-29 的死亡事故已经证明 `SavedVariables` 落盘当反馈不可靠。这一轮又暴露了
第二个问题：**`last_reason` 会被施法事件冲掉**。

客户端的事件顺序是：

1. `UNIT_SPELLCAST_FAILED`（kind=3，reason=0）——施法失败，原因未知
2. `UI_ERROR_MESSAGE`（kind=5，reason=5）——客户端解释失败原因

`last_reason` 只保留最后一个事件，所以第 1 步就把第 2 步的 reason=5 覆盖成了 0。
协议 v5 新增 `last_error_reason`，**只在 UI 错误到达时更新**，不会被施法事件覆盖。
实测证明这个字段是朝向闭环唯一的可靠反馈信号。

## 转向速率标定

`results/client_turn_measure_*.json` 用位移向量测了转向速率：

| 转向时长 | 航向变化 |
| --- | --- |
| 0.3 秒 | 61° |
| 0.8 秒 | 135° |

即约 **170°/秒**。这个标定值直接决定两个参数：

- 转向步长定为 0.06 秒（约 10°），避免一步跨过目标方向。
- 早期版本用 0.45 秒 × 10 步（约 770°，整整两圈），结果又转回正面，
  施法照样命中——这是第一次验证"转过去了却仍命中"的原因。

## 目标选取是验证的关键

**必须选射程内且血量足够的敌对单位**，否则信号会被别的失败盖掉：

| 目标 | 现象 | 结论 |
| --- | --- | --- |
| 村内鸡（1 血，射程外） | 连续 18 次施法全部 `reason=1`（range） | 真射程问题，与朝向无关 |
| 村内鸡（1 血，射程内） | 转向后仍能命中 | 鸡目标已死，或未真正偏离正前方 |
| 野外狼（120 血，射程内） | 转向后 `reason=5`，转回后命中掉 21 血 | **有效样本** |

早期几轮之所以"转过去还能打中"，是因为目标本身在射程外，客户端报的是 range。
只有拿到射程内的目标，朝向信号才干净。

## 探测到 Probehuman 无法复活

角色 Probehuman 在 Northshire Valley 死亡后，服务端把它存成了 **Ghost** 状态，
角色选择界面直接标注 `Probehuman Level 1 Mage (Ghost)`。

在这个状态下，**客户端不响应任何输入**：

| 手段 | 结果 |
| --- | --- |
| 右键幽灵 / 名牌 / NPC 菜单 | 无反应 |
| 小地图导航、点击墓碑 | 无反应 |
| 走位到复活点 | 位置每步只变 0.002，够不到释放点 |
| GM 命令 `/revive` `/heal` `/unlearn all` | 无效，幽灵态不处理聊天命令 |
| `/run AcceptResurrect()` / `/run Resurrect()` | 无效，同上 |
| 客户端重启后重新登录 | 仍然是 Ghost，血量 1/52 |
| 点击游戏菜单 Logout | **有效**，回到角色选择界面 |

该墓地区域**没有释放点蜡烛**（整个区域呈灰蓝色幽灵着色，找不到暖色光源），
服务端也没有把 1 级角色配置成自动复活。

最后用账号下的另一个角色 **Syra（Level 7 Mage）** 完成了本轮全部实机验证。
账号和客户端本身是健康的，问题只在 Probehuman 这个角色的服务端状态。

## 观测方法上的一个教训

**「转过去施法还命中」不能直接当成「转向无效」**。这轮第一次转向验证就是这样
误判的：转向逻辑当时是对的，但目标在射程外，失败原因是 range。

同一个教训在 2026-10-29 也出现过一次：任务失败不等于脱战。
**判定必须绑定到具体的原因码和证据，不能靠「看起来没生效」推断。**

## 仍未验证

- 转向闭环只在 1 个敌对目标（120 血狼）上验证过，未覆盖多目标、
  移动目标、远程敌人。
- 施法 0.45 秒结算的前提是火球术；其他法术的施法时间不同，
  `CastProbe.settle` 需要按法术调整。
- 客户端的射程判定本身也受朝向影响（目标在视野外时报 range 而不是 facing），
  所以 reason 1 与 reason 5 的区分依赖目标确实在射程内。
- 中文界面的错误文本仍只匹配英文关键字。
- Probehuman 仍是 Ghost 状态，需要服务端侧修正或重建角色。
