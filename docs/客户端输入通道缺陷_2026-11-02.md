# 客户端输入通道的三个真实缺陷

本轮实机验证过程中发现了三个互相独立的输入通道缺陷。它们都表现为
「命令发出去了但客户端没有任何反应」，很容易被误判成协议或逻辑问题。

## 一、隐藏的控制台窗口仍然是前台窗口

计划任务在交互会话里运行自己的控制台。`hide_consoles()` 用
`ShowWindow(SW_HIDE)` 把它隐藏了，但**隐藏不等于失去焦点**：
`GetForegroundWindow()` 仍然返回那个 cmd.exe 窗口。

系统的键盘输入只送给前台窗口。SendInput 的按键因此进了控制台，
游戏一次也没收到。

证据：`.cache/desktop-check/window-state.json` 里

```json
{
  "hwnd": 6161930,
  "is_foreground": false,
  "foreground_class": "ConsoleWindowClass",
  "foreground_title": "C:\\Windows\\system32\\cmd.exe"
}
```

游戏窗口可见（`visible: true`、未最小化、rect 覆盖全屏），但不是前台。

**修正**：新增 `client_chat_guard.ensure_focus()`，在**每一次键盘输入之前**
检查前台窗口，不是只在脚本开头调用一次。

修正前后的直接对比是 hunt 的位置记录：

| 阶段 | 位置变化 |
| --- | --- |
| 修正前 | 10 轮完全相同（0.41213092240787363, 0.7305104142824445） |
| 修正后 | 0.4348→0.4505, 0.745→0.611，每轮都在动 |

## 二、聊天输入框会吞掉移动键

客户端的聊天输入框打开时，所有按键都进入文本框而不是角色。
一次失败的施法命令在聊天框里残留了内容，之后按 W 键时
屏幕上出现的是 `Say: awwwww`，角色纹丝不动。

探针从协议 v5 起就报告 `chat_open`，但驱动侧一直没有用它。

**修正**：新增 `client_chat_guard.ensure_chat_closed()`，
在发命令和移动之前检查 `chat_open`，为真时按 ESC 关闭。
关闭动作本身也需要焦点，所以它先调用 `ensure_focus()`。

## 三、世界地图会遮住整个画面

点击小地图时如果点到了地图按钮，客户端会打开世界地图。
地图是一个覆盖全屏的窗口，**探针的面板被挡住，遥测完全无法解码**，
脚本只能报 `live telemetry absent or invalid`。

**修正**：

- 小地图点击限制在圆形地图区域内（中心 1800,145，半径 82 像素），
  超出区域就不点；
- 新增 `close_world_map()`，点击地图窗口右上角的关闭按钮（1857, 45），
  并用遥测是否恢复来确认地图确实关掉了；
- 所有脚本启动时先调用一次，因为之前留下的地图会一直挡着。

这一条还暴露了一个检测错误：地图关掉之后，**角色选择界面同样能解码遥测**
（探针是 addon，游戏界面切换后它仍然存在）。所以「遥测能解码」不能用来判断
「是否在世界里」。现在改用画面上的红色 Enter World 按钮来判断。

## 附带的输入约束

`client_facing.turn_step()` 与 `client_retreat.hold()` 也都用 SendInput，
所以它们同样需要焦点保证。两者现在都接受 `hwnd` 参数。

## 测试

新增 `scripts/test_client_chat_guard.py`，5 项测试覆盖：

- 聊天框关闭时不发任何按键；
- 聊天框打开时用 ESC 关闭；
- 聊天框关不掉时报错；
- 遥测读取失败时按「已关闭」处理，不阻塞输入；
- 焦点保证在移动前被调用。

离线测试总数 88 项全部通过。
