## v9（125 字节）

在 v8 的事件队列之后、校验和之前新增三段：

| 字段 | 长度 | 内容 |
| --- | --- | --- |
| `player_guid` | 8 | 玩家自己的 GUID（十六进制，与目标 GUID 同格式） |
| `target_name_hash` | 2 | 目标名字的哈希（djb2 变体，16 位） |

**为什么名字走哈希**：面板的字节条只能放数字，放不下字符串。名字的哈希在
Lua 与 Python 两侧各算一遍即可比较：

```lua
local function name_hash(text)
  local hash = 5381
  for i = 1, #text do
    hash = (hash * 33 + string.byte(text, i)) % 65536
  end
  return hash
end
```

```python
def name_hash(text):
    digest = 5381
    for value in text.encode('utf-8'):
        digest = (digest * 33 + value) % 65536
    return digest
```

实测：`"Diseased Young Wolf"` → 46929，`"Diseased Timber Wolf"` → 22786，
`"Probehuman"` → 7254，空串 → 5381。

## v9 落地时踩到的三个坑（都写进了离线测试）

1. **长度字节是硬编码的**。Lua 里写的是 `number(115, 1)`，改了
   `DATA_BYTES` 也不会跟着变 → 解码器校验长度对不上 → 面板"读不出来"。
   现在写 `number(DATA_BYTES, 1)`，并有测试断言"Lua 声明的字节数 == 布局总长"✓。
2. **解码器试尾标偏移时漏了新版本**。`decode()` 里是一个固定元组
   `(V8_TRAILER_OFFSET, ...)`，加了 v9 忘了加 → v9 的面板永远找不到尾标 →
   面板能画出来但解不出来 ✓。现在 v9 在元组第一位 ✓。
3. **玩家 GUID 的格式**。一开始按经典服的 `Player-<realm>-<id>`（十进制）去解析，
   结果全解成 0 ✓；实际这个 3.3.5a 客户端给的是十六进制 GUID
   （面板里 `player=0x0000000000000008`）✓ → 改回十六进制解析 ✓。
   教训：格式先在面板上打出来看一眼，再写解析器 ✓。
