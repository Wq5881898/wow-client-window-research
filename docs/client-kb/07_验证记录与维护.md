## 每次测试如何使用知识库

1. 按现象找到问题编号，核对版本与当前代码是否已经变化。
2. 记录一个主要假设，选条目中的最小区分实验；无需把整张表都跑一遍。
3. 收到结果后区分：现象已复现、原因已确认、修复已实现、离线已通过、实机已通过。它们可以是不同进度。
4. 把反例及证据写入独立报告，再更新对应问题的状态、范围、账本和来源编号。
5. 若推翻旧解释，在条目上写SUPERSEDED及更正指向，保留失败原件与旧run ID。

## 验证记录模板

复制下面内容到独立新报告；每份报告应链接回问题条目。不要把尚未运行的计划填成成功结果。

```markdown
# 验证记录：问题编号 / 任务名 / 日期

- 问题编号：例如REC-01
- 对应知识条目：docs/client-kb/04_恢复与验收.md#rec-01
- 执行窗口与任务：A3等
- 状态：计划 / 现象复现 / 原因确认 / 已实现 / 离线通过 / 实机通过 / 失败 / 结果未知
- 客户端版本/build/interface、服务端版本：
- 代码提交或工作区差异、探针部署版本：
- 场景与角色GUID/地图身份：不放密码、令牌或认证缓存
- 假设与至少一个替代解释：
- 本次变量 / 保持一致的条件：
- 操作或离线输入 / 时间预算 / 必需恢复分支：
- 预先定义的通过、拒绝和未知条件：
- 实际结果：逐条事实及时间
- 证据：父子run ID、报告/trace/截图路径，必要时SHA-256
- 反例：修复前行为、修复后拒绝或通过行为
- 结论：只覆盖本次版本和场景
- 剩余未知与下一动作：
- 更新知识条目/来源/账本：具体路径
```

## 维护约定

- 不改写既有run的结果来“修成功”；代码修复用新反例、新结果证明。
- 外部项目引用优先固定commit/file；issue评论带URL与日期；可变网页注明取得日期和阅读范围。
- 把作者功能声明与本地实测分开；“未支持”也标明是谁对哪个版本作出的判断。
- 新条目用唯一稳定编号，并在README登记关键词；避免同一问题在多个文件分别维护完整当前状态。
- 操作手册维护现行流程，知识库维护问题与证据，原研究文档保留取证底稿；内容冲突时核查最近实际证据，不按文件名“最新”盲选。
- 两个执行窗口各写独立验证报告，集中维护入口时先确认无并发修改；客户端同一时间只有一个执行流操作。
